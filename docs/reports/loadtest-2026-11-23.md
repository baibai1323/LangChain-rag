# 压测报告 · 40 用户容量验证

- 日期：2026-11-23
- 目标：验证「40 人同时使用」是否成立，并找出瓶颈
- 实例：本机 uvicorn 单 worker，`127.0.0.1:8001`，数据目录 `.loadtest/data`（2 库 8 文档），Windows 11 / Python 3.14
- 工具：`scripts/loadtest.py`（SSE 真实链路，非 mock），模型走百炼真实 API

## 1. 场景与结果

### 1.1 认证链路

| 场景 | 并发 | p50 | p95 | 结果 |
|---|---|---|---|---|
| 注册 | 50 | 1.41s | 2.34s | 50/50 成功 |
| 登录（30% 错密码） | 100 | 2.73s | 4.64s | 71×200 + 29×401，无 5xx |
| 令牌链路 login→me→refresh→logout | 100 | 5.41s | 5.75s | 全部成功 |

Argon2 校验已从事件循环卸载到线程池，并用信号量限制在 8 路并发，避免 100 并发把内存打爆。

### 1.2 问答冷链路（关闭缓存）

| 到达方式 | 请求数 | 首字 p50 | 首字 p95 | 总耗时 p50 | 总耗时 p95 | 错误 |
|---|---|---|---|---|---|---|
| 40 人同一秒涌入 | 41 | 15.03s | 23.79s | 16.66s | 25.71s | 0 |
| 40 人在 40 秒内均匀到达（≈1 人/秒） | 95 | **1.48s** | **2.04s** | 3.17s | 5.00s | 0 |

结论：**40 用户在正常到访节奏下可以支撑，首字 p95 约 2 秒**；但 40 人同一秒同时提问会触发模型侧排队，首字退化到 15–24 秒。

|---|---|---|

## 2. 瓶颈与修复

1. **改写调用被 429 打爆**：高并发下 qwen-turbo 每次都失败并触发重试，把首字拖到 13 秒。
   修复：`needs_rewrite()` 只对带指代/省略的短问句改写；失败后 60 秒冷却直接使用原问题。
2. **重试叠加**：`_with_retry` 与外层 SDK 重试相乘。修复：SDK `max_retries=1`，重试函数增加总预算，预算不够一次退避就直接降级。
3. **SQLite 偶发 `unable to open database file`**：高并发写 WAL 时 Windows 文件占用导致，3/76 请求在落库阶段失败。修复：落库失败重试一次，最终 95/95、41/41 全部成功。
4. **限流被伪造头绕过**：`X-Forwarded-For` 只在 `TRUST_PROXY_HEADERS=true` 时才信任。

## 3. 仍存在的限制

- **模型侧并发是硬约束**：40 个请求同一秒到达会排队；要消除这一点，需要提高百炼配额或加多把 API Key 轮询。
- **单 worker**：`metrics`、限流、语义缓存都是进程内状态，直接多开 worker 会导致统计与限流不一致；要横向扩展需先把这些状态外置（Redis 等）。
- 本报告不含前端静态资源压测，前端由 FastAPI 直接托管，静态文件不是瓶颈。

## 4. 简历可用表述

> 用真实链路压测 40 用户：错峰到访下问答首字 p50 1.48s / p95 2.04s、0 错误；定位并修复 429 重试叠加（首字 13.7s → 1.5s）、SQLite 并发写偶发失败、Argon2 阻塞事件循环三个问题。
